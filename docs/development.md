# Development and contributions

OSymbiote is an early-stage project. Changes should remain small, testable, and explicit about what has and has not been validated.

## Source layout

| Path | Contents |
|---|---|
| `VERSION` | Canonical project release version |
| `scripts/overlay/` | Guest PID 1, `osh`, HTTP handler, shared shell library, portal, and COMB tool |
| `scripts/build-phase1.sh` | x86_64 image builder and generated `boot.sh`/`test.sh` helpers |
| `scripts/build-arm64.sh` | ARM64 QEMU `virt` image builder |
| `run.sh` | x86_64 QEMU launcher |
| `run-arm64.sh` | ARM64 QEMU `virt` launcher |
| `docs/` | User, API, architecture, security, operations, and contributor documentation |

Make guest behavior changes under `scripts/overlay/`; both architecture builders install that shared overlay. Keep generated build outputs and persistent guest data out of source control.

## Build and validation

Build images:

```sh
bash scripts/build-phase1.sh
bash scripts/build-arm64.sh
```

Available shell checks:

```sh
bash -n scripts/build-phase1.sh scripts/build-arm64.sh run.sh run-arm64.sh
sh -n scripts/overlay/init scripts/overlay/agent_handler.sh scripts/overlay/lib.sh scripts/overlay/osh scripts/overlay/comb
shellcheck scripts/build-phase1.sh scripts/build-arm64.sh run.sh run-arm64.sh scripts/overlay/init scripts/overlay/agent_handler.sh scripts/overlay/lib.sh scripts/overlay/osh scripts/overlay/comb
```

`./test.sh` is generated by the x86_64 builder and expects a running guest. For an integration check, boot the image in QEMU and run `./test.sh` from another shell. Provider checks require an explicitly supplied test authorization header; do not place real credentials in commits or command histories.

An image build is not a runtime boot test. Record the target, host, exact validation performed, and any unavailable hardware/emulator in change descriptions.

## Contribution workflow

1. Read the root [README](../README.md), this document, and relevant implementation files.
2. Keep documentation claims aligned with tested implementation behavior.
3. Test both architecture builds when shared guest files or build logic change.
4. Do not commit build output, `data/`, passwords, API keys, cookies, or other secrets.
5. Include the observable behavior, tests, and remaining limitations in the pull request.

## Documentation conventions

- Use relative links within the repository and descriptive headings.
- Label implemented, unverified, and planned features separately.
- Prefer versioned release notes in `CHANGELOG.md`; do not add independent version numbers to individual source files.
- Keep `VERSION` as the sole canonical project version and update version consumers when changing it.
